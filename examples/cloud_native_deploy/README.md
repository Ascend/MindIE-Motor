# Cloud-Native Deploy

This directory provides a cloud-native deploy flow for `examples/deployer/deploy.py`.

It is intended for platform-triggered deployment and does not depend on logging into a host machine or using host-local files.

## Why this exists

The original deploy flow assumes an operator logs into a Kubernetes node and runs `examples/deployer/deploy.py` manually with local config files.

That works for manual verification, but it becomes difficult to operate in a real cloud platform environment:

- Multi-tenant clusters usually run multiple inference services at the same time and isolate them by namespace.
- Platform users should not need shell access to cluster nodes.
- Deployment requests are usually submitted through platform APIs or control planes, not by running scripts on a host.
- Delivery artifacts should be immutable container images and Kubernetes manifests, not host-local generated files.
- Scale and cleanup operations should also be expressed as Kubernetes Jobs so that the platform can audit, retry, and observe them.

This directory packages the existing deploy logic into a container-friendly form so that a cloud platform only needs to:

1. Prepare a ConfigMap that contains `user_config.json` and `env.json`.
2. Launch a Kubernetes Job for deploy, scale, or cleanup.

The deploy implementation itself is still the existing `examples/deployer/deploy.py`, which keeps behavior aligned with the current manual workflow while making the entrypoint cloud-native.

## Build image

From repo root:

```bash
docker build -f examples/cloud_native_deploy/Dockerfile -t mindie-motor-deployer:latest .
```

Or use the root Makefile:

```bash
make buildx-cloud-native-deployer TAG=latest
```

## Prepare config

Edit `k8s/configmap-user-config.yaml` and paste both your `user_config.json` and `env.json`.

For production, configure inference TLS and management API Key authentication in `user_config.json`
before deploying or scaling. See the exact fields in the [security pre-check guide](../deployer/README.md#安全预检).
Keep the pre-check enabled and remove any saved `--skip-check` from Helm values or Job arguments.
`--skip-check` is only for isolated local or test environments; do not use it in production.

Optional:

- `motor_deploy_config.scheduling_queue` selects the Volcano queue. Motor writes it to the RBG
  annotation `rbg.workloads.x-k8s.io/group-gang-scheduling-volcano-queue`, which RBG v0.8.0 reads,
  so it controls the RBG group queue when gang scheduling is enabled. Verify the queue exists and
  `scheduler_name` is `volcano`. In RBG mode, changing the queue requires redeployment.
- Set `motor_deploy_config.coordinator_service_name` to override the external inference Service name.
- Set `motor_deploy_config.coordinator_infer_node_port` to override the inference Service NodePort. Use `"-"` for Kubernetes allocation; omitting it keeps the `nodePort` configured in the template, which currently defaults to `31015`.
- Set `motor_deploy_config.encode_node_selector`, `motor_deploy_config.prefill_node_selector`, and `motor_deploy_config.decode_node_selector` to control Encode/Prefill/Decode node placement separately.
- Set `motor_deploy_config.controller_node_selector` and `motor_deploy_config.coordinator_node_selector` to control Controller/Coordinator placement separately.
- Set `motor_deploy_config.kv_pool_node_selector` and `motor_deploy_config.kv_conductor_node_selector` to control KV Pool/KV Conductor placement separately.

## Deploy with Helm

The community `helm/` chart creates the ConfigMap, ServiceAccount, RBAC, and deploy/scale/cleanup Jobs. Runtime resources are still generated by `examples/deployer/deploy.py` inside the Job.

See the [Helm security precheck](helm/README.md#deployment-security-precheck) for the required configuration and how to pass `--skip-check` to a deploy or scale Job in an isolated test environment.

Copy and edit the default values, including both the deployer image and the Motor runtime image:

```bash
cp examples/cloud_native_deploy/helm/values.yaml /tmp/motor-values.yaml

helm upgrade --install motor examples/cloud_native_deploy/helm \
  --namespace mindie \
  --create-namespace \
  --values /tmp/motor-values.yaml \
  --set operation=deploy
```

Use `operation=scale` after changing the instance counts. To remove runtime resources, run `operation=cleanup` before `helm uninstall`.

See [the Helm chart README](helm/README.md) for details.

## Deploy with RBG

Use a code version that includes the RBG implementation and samples, and a deployer image built from that version.

RBG (RoleBasedGroup) samples are provided as:

- Helm: `helm/values-rbg.yaml`. It only overrides `operation` and `userConfig`; the image,
  `envConfig`, and Jobs still come from the chart defaults. Its `userConfig` differs from the
  default sample only in `deploy_mode: "rbg"` and the added `rbg_config` section.
- Plain kubectl: `k8s/configmap-user-config-rbg.yaml`, identical to the `userConfig` above and meant
  to replace the default `k8s/configmap-user-config.yaml`.

Install and run the RBG v0.8.0 controller and its CRDs first. The sample enables gang scheduling,
so install Volcano and configure the RBG controller with `--scheduler-name=volcano`
(`controller.features.gangScheduling.schedulerName=volcano` in the RBG Helm chart).
The controller defaults to `scheduler-plugins`; setting Motor's `rbg_config.scheduler_name` does
not configure the controller. See the [RBG prerequisites](../deployer/lib/rbg/README.md#前置条件).

For the prerequisite installation commands and verification steps, see the
[RBG prerequisite installation](../deployer/lib/rbg/README.md#前置组件安装). Run these commands from
the Motor source root; use an unused absolute directory for `RBG_SOURCE_DIR`:

```bash
# Volcano: install the MindCluster Volcano package and apply its YAML
kubectl apply -f volcano-v{version}.yaml

# RBG v0.8.0
RBG_SOURCE_DIR=/tmp/rbg-v0.8.0
git clone --branch v0.8.0 --single-branch https://github.com/sgl-project/rbg.git "$RBG_SOURCE_DIR"
helm upgrade --install rbgs "$RBG_SOURCE_DIR/deploy/helm/rbgs" \
  --create-namespace --namespace rbgs-system \
  --set controller.features.gangScheduling.schedulerName=volcano --wait
```

Keep one RBG per namespace. Instance-linked rebuilds use the RBG `restartPolicy`. RAS (`ras_monitor`)
still deletes and redeploys the whole service through the legacy `delete.sh`, without the data-PVC
retention semantics of the RBG cleanup path, so it is not recommended for RBG recovery. Deleting a
single Pod only recreates that Pod, not the whole instance. See the
[ras_monitor guide](../features/fault_tolerance/ras_monitor/readme.md).

After copying the RBG values, set the deployer image, Motor runtime image in `userConfig`, model
paths, `job_id`, instance counts, NPU counts, hardware type, node selectors, and `envConfig` for
your environment. The sample's empty runtime image must be filled in before deployment.

The RBG samples use `hardware_type: "800I_A3"`, one Pod per P/D instance, and 16 NPUs per Pod.
This A3 sample is not the A5 DeepSeek-V4.1-Flash configuration. For A5, use
`model_configs/vllm/models/deepseek_v4.1_flash/A5/`: `hardware_type: Ascend950`, P/D 1/1, one Pod
per instance, 8 NPUs per Pod, P/D DP×TP×PP of 8×1×1, KV memcache inprocess, and P/D
`HCCL_OP_EXPANSION_MODE=CCU_SCHED`. Do not only change `hardware_type` in the A3 sample.
For A2/A5 or another model, replace the embedded JSON with the matching model/hardware configuration,
then apply the [A2/A3/A5 field changes](../deployer/lib/rbg/README.md#a2a3a5-配置调整) and the
[A5 parameter table](../deployer/lib/rbg/README.md#a5-deepseek-v41-flash-部署参数).
Edit `userConfig` and `envConfig` for Helm; for plain kubectl, edit `data.user_config.json` and
`data.env.json` in `k8s/configmap-user-config-rbg.yaml`. The adapter rejects `*-sp` supernode affinity,
and default gang scheduling rejects different hardware policy combinations across active roles.
MindCluster supports A3/A5 supernode scheduling; the restrictions above belong to the current Motor
RBG adapter. A3 `sp-block` defines logical supernode blocks, while the default A5 `chip8-node8`
selects a node-local interconnect policy. Matching P/D annotations do not prove that the hardware
policy is active. A shared real supernode member selector can constrain placement, but does not
complete the scheduling integration. Review the
[scheduling limits](../deployer/lib/rbg/README.md#调度规格限制), including the A2 multi-Pod gang count
and A3 MultiConnector configuration issues, before migration.
RBG also rejects P2D and container snapshots. The
[complete rbg_config example](../deployer/lib/rbg/README.md#完整-rbg_config-示例) explains fields,
defaults, and update restrictions; the [acceptance checks](../deployer/lib/rbg/README.md#部署后验收)
cover workload readiness and inference after resource submission.

Configure inference TLS and a management API Key before deploying; keep the security pre-check enabled:

```bash
cp examples/cloud_native_deploy/helm/values-rbg.yaml /tmp/motor-rbg-values.yaml
# Edit /tmp/motor-rbg-values.yaml for your environment before deploying

helm upgrade --install motor examples/cloud_native_deploy/helm \
  --namespace mindie \
  --create-namespace \
  --values /tmp/motor-rbg-values.yaml \
  --set operation=deploy
```

Scaling reuses `--set operation=scale` with the security pre-check enabled. This operation changes
only instance counts, and the target role must no longer be managed by an HPA or ScalingAdapter. See the
[RBG scaling guide](../deployer/lib/rbg/README.md#扩缩容) for enabling, preserving, and disabling HPA.
Cleanup uses `--set operation=cleanup`: it handles HPAs, deletes the RBG, waits for descendants to
exit, then removes business attachments and runtime configuration. Data PVCs and external resources
are retained. The Helm cleanup Job reads `userConfig.motor_deploy_config.deploy_mode` and sets
`MOTOR_DEPLOY_MODE=rbg` automatically, so run cleanup with the RBG values file (or another values file
that keeps `deploy_mode: rbg`). For the plain kubectl path, set `MOTOR_DEPLOY_MODE: "rbg"` in
`k8s/cleanup-job.yaml` before applying it. Uninstall the Helm release after cleanup completes.
Also configure the same security settings in the ConfigMap for the plain kubectl path, and leave
`--skip-check` out of `k8s/job.yaml` and `k8s/scale-job.yaml` in production.
Use `k8s/clusterrole.yaml` or Helm RBAC from the same integrated RBG code version as the deployer
image, and check the full [deployer permission list](../deployer/lib/rbg/README.md#部署账号-rbac).
Do not assume the selected branch already contains the RBG and HPA rules. Adding only RBG `list`
is insufficient; check RBG, CoordinatedPolicy, Adapter, HPA, and runtime resource permissions before
deploying or updating policies.

See the RBG section in the [deployer README](../deployer/README.md) for configuration fields,
prerequisites, and limitations.

## Apply RBAC and run

The deploy Job checks that `user_config.json` enables inference TLS and management API key
authentication and specifies an API key file path. Complete the
[security configuration](../../docs/zh/user_guide/deployment/k8s/README.md#deployment-security-precheck)
before a production deployment. For isolated tests that need to use the current configuration,
add `args: ["--skip-check"]` to the `deployer` container in `k8s/job.yaml` before creating the Job.

The following commands use the default config. For RBG, substitute
`configmap-user-config-rbg.yaml` and complete the image, config, and Job argument settings above.

```bash
kubectl apply -f examples/cloud_native_deploy/k8s/serviceaccount.yaml
kubectl apply -f examples/cloud_native_deploy/k8s/clusterrole.yaml
kubectl apply -f examples/cloud_native_deploy/k8s/clusterrolebinding.yaml
kubectl apply -f examples/cloud_native_deploy/k8s/configmap-user-config.yaml
kubectl apply -f examples/cloud_native_deploy/k8s/job.yaml
```

Check logs:

```bash
kubectl logs job/mindie-motor-deploy -n mindie
```

## Scale

The scale Job runs the same security precheck. For isolated tests that need to use the current
configuration, add `args: ["--skip-check"]` to the `scaler` container in `k8s/scale-job.yaml`
before creating the Job.

Update `p_instances_num` and/or `d_instances_num` in your ConfigMap
(`k8s/configmap-user-config-rbg.yaml` for RBG), re-apply it, then run the following command.
An RBG target role must no longer be managed by an HPA or ScalingAdapter.

```bash
kubectl apply -f examples/cloud_native_deploy/k8s/scale-job.yaml
kubectl logs job/mindie-motor-scale -n mindie
```

## Cleanup

The cleanup Job requires a target namespace. For an RBG deployment, edit
`k8s/cleanup-job.yaml` and set `MOTOR_DEPLOY_MODE` to `"rbg"` before applying it; the default empty
value runs the legacy cleanup flow.

```yaml
env:
  - name: NAMESPACE
    value: mindie
  - name: MOTOR_DEPLOY_MODE
    value: "rbg"
```

```bash
kubectl apply -f examples/cloud_native_deploy/k8s/cleanup-job.yaml
kubectl logs job/mindie-motor-cleanup -n mindie
```
