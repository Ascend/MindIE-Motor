# Building the MkDocs Documentation Service Locally

<!-- md-trans-meta sourceCommit=unknown translatedAt=2026-06-27T02:07:34.611Z pushedAt=2026-06-29T07:00:39.394Z -->

This document describes the layout of **MkDocs** within the repository, how to preview locally and build statically, and the configurations that need to be updated synchronously when adding or modifying Markdown pages under **`docs/en`** (especially **`docs/en/.nav.yaml`**).

The site entry is **`mkdocs.yml`** at the repository root (with `docs_dir` pointing to **`docs/en`**). The sidebar navigation is not maintained by the `nav` field in `mkdocs.yml`; instead, it is generated by the **`mkdocs-awesome-nav`** plugin reading **`docs/en/.nav.yaml`**.

## MkDocs-Related Directory Structure 

All paths below are relative to the repository root.

```text
MindIE-PyMotor/
├── mkdocs.yml                    # Main MkDocs configuration (theme, plugins, extensions, extra_css/js, etc.)
├── .readthedocs.yaml             # Read the Docs online build (Python version, dependency installation, fail_on_warning)
├── requirements/
│   └── mkdocs.txt                # pip dependencies dedicated to documentation building
├── docs/
│   ├── mkdocs/                   # Documentation engineering resources (hooks, custom styles and scripts), the logical "canonical" directory
│   │   ├── hooks/                # Hooks such as on_page_markdown (see below)
│   │   ├── stylesheets/
│   │   │   └── extra.css         # Global extra styles (referenced by extra_css in mkdocs.yml)
│   │   └── javascripts/
│   │       └── mathjax.js        # MathJax configuration script (referenced by extra_javascript in mkdocs.yml)
│   └── en/                       # MkDocs document root directory (docs_dir in mkdocs.yml)
│       ├── mkdocs/               # → Symbolic link pointing to ../mkdocs, so that extra_css/js paths fall within docs_dir and are copied correctly
│       ├── .nav.yaml             # Sidebar navigation tree (awesome-nav)
│       ├── index.md              # Site homepage
│       ├── assets/               # Static assets referenced by the theme (e.g., logo, favicon; see mkdocs.yml)
│       ├── user_guide/           # Directory for Markdown content such as user guides (subdirectories can be added as needed)
│       ├── developer_guide/
│       ├── api_reference/
│       └── ...
└── site/                         # Default output directory for mkdocs build (usually not committed to the repository)
```

Key points:

- **All body Markdown** must be placed under **`docs/en/`** (including subdirectories); MkDocs will only scan this directory tree as the document source (and determine navigation in conjunction with `.nav.yaml`).

- **`docs/mkdocs/`** stores scripts and static resources related to the "documentation site engineering"; **`docs/en/mkdocs`** links to **`docs/mkdocs`**, so that `extra_css` / `extra_javascript` can use paths like **`mkdocs/stylesheets/extra.css`** (relative to **`docs/en`**), ensuring the static URLs in the build output are correctly mapped. **If the repository is cloned on Windows and the symbolic link is abnormal**, you need to maintain an equivalent link or copy under **`docs/en`** to ensure the files exist at the above paths.

- Python files in **`docs/mkdocs/hooks/`** are registered in **`hooks:` of `mkdocs.yml`**; they are not Markdown pages and will not appear in the navigation.

## How to Add a New Markdown Document

1. **File Creation**

   Select a category directory under **`docs/en/`** (for example, `user_guide/`, `developer_guide/`), and create a new **`*.md`** file. The path should match the document type to facilitate retrieval and review.

2. **(Required) Navigation Updates**

   Edit **`docs/en/.nav.yaml`** and add a line **`Display title: path relative to docs/en`** at the appropriate level.

   - If you only add a file without modifying `.nav.yaml`, the page can still be accessed directly via the URL (if not excluded by the plugin), but **it will not appear in the sidebar** and is likely to be flagged as "inconsistent with the document entry" during the gate link check.

   - The order of sibling entries determines the sidebar order; multi-level directories use YAML nesting (see the next section).

3. **Self-check Links and Anchors**

   - For intra-site page links, it is recommended to use **paths relative to `docs/en`**, such as **`/user_guide/quick_start.md`** (consistent with MkDocs/Material's document root resolution), or **`service_deployment/config_reference.md`** relative to the current file. The **`link-validity-check`** gate often validates local Markdown links against **`docs/en`** as the base, avoiding targets that cannot be resolved within the site, such as repository root paths or `../../../examples/...`.

   - You can use **`mkdocs serve --strict`** or **`mkdocs build --strict`** to expose warnings such as broken links and missing anchors.

4. **(Optional) Images and Other Static Files**

If images and other files are placed under **`docs/en`**, use paths relative to the current Markdown file. If you use the HTML `<img width="...">` syntax supported by **`docs/mkdocs/hooks/img_width.py`**, it will be converted to the attribute syntax compatible with Material during the build.

## Navigation Configuration (`.nav.yaml`)

The **`mkdocs-awesome-nav`** plugin reads **`docs/en/.nav.yaml`**. The top-level structure is generally:

```yaml
nav:
  - Home: index.md
  - Group Title:
      - Subpage: path/under/docs_en.md
      - Deeper Group:
          - Item: nested/page.md
```

Summary of rules:

- **Key (text on the left)**: title displayed in the sidebar.

- **Value (path on the right)**: Markdown path relative to **`docs/en`**, using **`/`** as the separator. Do **not** include the **`docs/en/`** prefix.

- **Nesting**: Use **`a_group_title:`** followed by an indented list on the next level to represent multi-level directories. Only leaf nodes need to be bound to **`*.md`** files.

After adding a new document, simply add the corresponding entry under the closest category. There is no need to modify the `nav` field in **`mkdocs.yml`** (this repository does not use that field to maintain navigation).

## Environment and Hooks

### Environment Requirements

- **Python**: **Version 3.11** is recommended (consistent with the online build in **`.readthedocs.yaml`**).

- **Dependency list**: **`requirements/mkdocs.txt`**, which mainly includes **`mkdocs`**, **`mkdocs-material`**, **`mkdocs-awesome-nav`**, **`mkdocs-glightbox`**, **`mkdocs-git-revision-date-localized-plugin`**, **`mkdocs-minify-plugin`**, **`mkdocs-redirects`**, and **`pymdown-extensions`**.

- **Hooks**: root directory **`docs/mkdocs/hooks/`** (enabled in the **`hooks:` under **`mkdocs.yml`**):

    - **`github_admonition.py`**: Converts GitHub/Obsidian-style **`>[!NOTE]`** / **`> [!NOTE]`** blockquotes into pymdown's **`!!! note`** for Material admonition rendering. If a blockquote contains nested **` ``` `** code fences, avoid extra spaces between **`>`** and the fence to prevent misaligned closing fences, which can cause **`#`** comment lines to be interpreted as Markdown headings.

    - **`img_width.py`**: Converts **`<img src="..." width="...">`** to **`![](){ width="..." }`** for width control.

### Writing Prompts (Common Pitfalls)

- **Fenced code language**: Use Pygments-supported names for fenced code block language identifiers (for example, use **`text`** for plain text, not **`Plain Text`**).

- **Material-specific syntax**: **`!!! note`** in the source code only renders in MkDocs. If you want it to be readable in general previews such as GitHub, prefer using **`>[!NOTE]`** and let the hook convert it (avoid placing "decorative indentation" such as exactly two spaces before **`>[!NOTE]`**, as this may affect parsing).

- **`extra_css` / `extra_javascript`**: Configure these in **`mkdocs.yml`** as paths relative to **`docs/en`** (currently **`mkdocs/stylesheets/extra.css`** and **`mkdocs/javascripts/mathjax.js`**), relying on **`docs/en/mkdocs`** pointing to **`docs/mkdocs`**.

## Installing Dependencies

Run the following command in the repository root directory:

```shell
pip install -r requirements/mkdocs.txt
```

## Starting Local Live Preview

Step 1: Run the following command in the project root to start the MkDocs local service (with hot reload on file changes):

```shell
mkdocs serve
```

Step 2: After successful startup, the terminal will output information similar to the following:

```text
INFO     -  Building documentation...
INFO     -  Cleaning site directory
INFO     -  Documentation built in 1.23 s
INFO     -  [12:00:00] Watching paths for changes
INFO     -  [12:00:00] Serving on http://127.0.0.1:8000/
```

Step 3: Access the address displayed in the terminal in your browser to preview the documentation (if multilingual or version paths are configured, use the actual output).

> [!NOTE]Note
>
> * **`mkdocs serve`** listens on port **`8000`** by default. If this port is occupied, you can specify a different address and port using **`-a`**, for example, **`mkdocs serve -a 127.0.0.1:8080`**.
> * To catch issues such as broken links or anchors early in the local environment, add **`--strict`**: **`mkdocs serve --strict`**. Read the Docs is currently configured with **`fail_on_warning: false`** (see **`.readthedocs.yaml`**), but you can still enable it locally to reduce silent errors.

## Static Build (Generating a Publishable Site)

To generate site artifacts that can be hosted on a static server (such as Nginx or object storage):

```shell
mkdocs build
```

The artifacts are output to the **`site/`** directory in the repository root by default. You can treat warnings as errors:

```shell
mkdocs build --strict
```

For the online documentation build process, see **`.readthedocs.yaml`** (which uses **`requirements/mkdocs.txt`** to install dependencies and reads the root **`mkdocs.yml`**).

## FAQs

### Dependency Installation Fails

If dependency conflicts or installation failures occur during **`pip install`**, it is recommended to use a virtual environment for isolation:

```shell
python -m venv .venv_mkdocs
source .venv_mkdocs/bin/activate
pip install -r requirements/mkdocs.txt
```

### YAML Parsing Error or `!!python/name:` Tag Exception

Extensions such as **`pymdownx.superfences`** and **`pymdownx.emoji`** in **`mkdocs.yml`** use the **`!!python/name:`** YAML tag, which is incompatible with PyYAML **`safe_load`**. The **`check-yaml`** hook in **`pre-commit`** has already been configured to **`exclude`** **`mkdocs.yml`** (see the repository's **`.pre-commit-config.yaml`**). If other local YAML validations raise warnings, you can similarly exclude **`mkdocs.yml`**.

### Navigation Not Updated as Expected

The navigation of this repository is driven by **`docs/en/.nav.yaml`**. After adding a new page, add an entry in this file and verify the YAML indentation. After saving, restart **`mkdocs serve`** to refresh the sidebar.

### `extra.css` / `mathjax.js` Preview Returns 404

If requests for **`mkdocs/stylesheets/extra.css`** or **`mkdocs/javascripts/mathjax.js`** return **404**, verify that **`docs/en/mkdocs`** is a valid symbolic link pointing to **`docs/mkdocs`**, and that the paths in **`mkdocs.yml`** are correct relative to **`docs/en`**.

### In-site Link Gate Reports "Local Path Inaccessible" Error

The gatekeeper typically resolves local links in Markdown with **`docs/en`** as the root. Avoid pointing to **`*.md`** files outside **`docs/en`** (unless you change them to in-site paths or bring the content into **`docs/en`**); descriptions of cross-repository example directories can be placed in **`examples/`** with the in-repository path explained in the body text, or use a browsing link based on **`repo_url`**.
