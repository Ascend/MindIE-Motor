# Building the MkDocs Documentation Service Locally

This document describes the layout of **MkDocs** in the repository, how to preview it locally and perform a static build, and the configurations that need to be updated in sync when adding or modifying Markdown pages under **`docs/en`** (especially **`docs/en/.nav.yaml`**).

The site entry configuration is in **`mkdocs.yml`** at the repository root (`docs_dir` points to **`docs/en`**). The sidebar navigation is not maintained by the `nav` field in `mkdocs.yml`; instead, it is generated by the **`mkdocs-awesome-nav`** plugin reading **`docs/en/.nav.yaml`**.

## MkDocs-related Directory Structure

All paths below are relative to the repository root directory.

```text
MindIE Motor/
├── mkdocs.yml                    # Main MkDocs configuration (theme, plugins, extensions, extra_css/js, etc.)
├── .readthedocs.yaml             # Read the Docs online build (Python version, dependency installation, fail_on_warning)
├── requirements/
│   └── mkdocs.txt                # pip dependencies dedicated to documentation building
├── docs/
│   ├── mkdocs/                   # Documentation engineering resources (hooks, custom styles and scripts), the logical "canonical" directory
│   │   ├── hooks/                # Hooks such as on_page_markdown (see below)
│   │   ├── stylesheets/
│   │   │   └── extra.css         # Global extra styles (referenced by extra_css in mkdocs.yml)
│   │   └── javascripts/
│   │       └── mathjax.js        # MathJax configuration script (referenced by extra_javascript in mkdocs.yml)
│   └── zh/                       # MkDocs documentation root directory (docs_dir in mkdocs.yml)
│       ├── mkdocs/               # → Symbolic link pointing to ../mkdocs, so that extra_css/js paths fall within docs_dir and are copied correctly.s paths fall within docs_dir and are copied correctly
│       ├── .nav.yaml             # Sidebar navigation tree (awesome-nav).
│       ├── index.md              # Site home page.
│       ├── assets/               # Static resources referenced by the theme (such as logo and favicon; see mkdocs.yml)
│       ├── user_guide/           # Markdown content directory for the user guide and other documents (subdivided into subdirectories as needed)
│       ├── developer_guide/      # Developer guide
│       ├── design/               # Design documents
│       └── ...
└── site/                         # Default output directory of mkdocs build (usually not committed to the repository)
```

Key points:

- **Body Markdown** files must all be placed under **`docs/en/`** (including subdirectories); MkDocs only scans this directory tree as the documentation source (and determines navigation in conjunction with `.nav.yaml`).

- **`docs/mkdocs/`** stores scripts and static resources related to the "documentation site project"; **`docs/en/mkdocs`** links to **`docs/mkdocs`**, so that `extra_css` / `extra_javascript` can use paths such as **`mkdocs/stylesheets/extra.css`** (relative to **`docs/en`**), allowing the static URLs in the build output to resolve correctly. **If the repository is cloned on Windows and the symbolic link is abnormal**, you need to maintain an equivalent link or copy under **`docs/en`** yourself to ensure that the files at the above paths exist.

- The Python files in **`docs/mkdocs/hooks/`** are registered in the **`hooks:`** section of **`mkdocs.yml`**; they are not Markdown pages and do not appear in the navigation.

## What to Do When Adding a New Markdown Document

1. **Creating the File**

   Select a category directory under **`docs/en/`** (for example, `user_guide/` or `developer_guide/`) and create a new **`*.md`** file. The path should be consistent with the document type as much as possible to facilitate retrieval and review.

2. **(Required) Updating the Navigation**

   Edit **`docs/en/.nav.yaml`** and add a line **`display title: path relative to docs/en`** at the appropriate level.

   - If you only add a file without modifying `.nav.yaml`, the page can still be accessed directly via its URL (if not excluded by a plugin), but **it will not appear in the sidebar**, and it is likely to be flagged as "inconsistent with the documentation entry" during the CI gate link check.

   - The order of entries at the same level determines the sidebar order; multi-level directories use YAML nesting (see the next section).

3. **Checking Links and Anchors**

   - For intra-site page links, it is recommended to use a **path relative to `docs/en`**, for example **`/user_guide/quick_start.md`** (consistent with the document root resolution of MkDocs/Material), or a path relative to the current file such as **`deployment/k8s/config_reference.md`**. The **`link-validity-check`** CI gate usually validates local Markdown links against **`docs/en`** as the base, so avoid targets that cannot be resolved within the site, such as repository root paths or `../../../examples/...`.

   - You can use **`mkdocs serve --strict`** or **`mkdocs build --strict`** to surface warnings such as broken links and missing anchors.

4. **(Optional) Images and Other Static Files**

   If images and the like are placed under **`docs/en`**, reference them using paths relative to the current Markdown file. If you use the HTML `<img width="...">` syntax supported by **`docs/mkdocs/hooks/img_width.py`**, it will be converted to the attribute syntax supported by Material during the build.

## Navigation Configuration (`.nav.yaml`)

The **`mkdocs-awesome-nav`** plugin reads **`docs/en/.nav.yaml`**, whose top level is generally:

```yaml
nav:
  - Home: index.md
  - Group Title:
      - Subpage: path/under/docs_zh.md
      - Nested Group:
          - Entry: nested/page.md
```

Rule summary:

- **Key (English on the left)**: the title displayed in the sidebar.

- **Value (path on the right)**: the Markdown path relative to **`docs/en`**, separated by **`/`**. Do **not** write the **`docs/en/`** prefix.

- **Nesting**: use **`a group title:`** followed by an indented list on the next level to represent a multi-level directory; only leaf nodes need to be bound to **`*.md`** files.

After adding a new document, add the corresponding entry under the closest category; there is no need to modify the `nav` field in **`mkdocs.yml`** (this repository does not use that field to maintain navigation).

## Environment and Hooks

### Environment Requirements

- **Python**: **3.11** is recommended (consistent with the online build in **`.readthedocs.yaml`**).

- **Dependency list**: **`requirements/mkdocs.txt`**, which mainly includes **`mkdocs`**, **`mkdocs-material`**, **`mkdocs-awesome-nav`**, **`mkdocs-glightbox`**, **`mkdocs-git-revision-date-localized-plugin`**, **`mkdocs-minify-plugin`**, **`mkdocs-redirects`**, and **`pymdown-extensions`**.

- **Hooks**: root directory **`docs/mkdocs/hooks/`** (enabled in the **`hooks:`** section of **`mkdocs.yml`**):

    - **`github_admonition.py`**: Converts GitHub/Obsidian-style **`>[!NOTE]`** / **`> [!NOTE]`** blockquotes into pymdown **`!!! note`** for Material to render admonition boxes. If a **` ``` `** code fence is nested inside the blockquote, avoid extra spaces between **`>`** and the fence, so that the closing fence does not become misaligned and cause **`#`** comment lines to be treated as Markdown headings.

    - **`img_width.py`**: Converts **`<img src="..." width="...">`** into **`![](){ width="..." }`** to control the width.

### Writing Tips (Common Pitfalls)

- **Fenced code language**: For fenced code block language identifiers, use names supported by Pygments (for example, use **`text`** for plain text, not **`Plain Text`**).

- **Material-specific syntax**: The **`!!! note`** in the source code is rendered only in MkDocs. If you want it to be readable in general previews such as GitHub, prefer **`>[!NOTE]`** and let the hook convert it (avoid placing "decorative indentation" such as just two spaces before **`>[!NOTE]`**, as this may affect parsing).

- **`extra_css` / `extra_javascript`**: Configure them in **`mkdocs.yml`** as paths relative to **`docs/en`** (currently **`mkdocs/stylesheets/extra.css`** and **`mkdocs/javascripts/mathjax.js`**), relying on **`docs/en/mkdocs`** pointing to **`docs/mkdocs`**.

## Installing Dependencies

Run the following command in the repository root directory:

```shell
pip install -r requirements/mkdocs.txt
```

## Starting Local Live Preview

Step 1: Run the following command in the project root directory to start the MkDocs local service (it watches for file changes and hot-reloads):

```shell
mkdocs serve
```

Step 2: After successful startup, the terminal outputs information similar to the following:

```text
INFO     -  Building documentation...
INFO     -  Cleaning site directory
INFO     -  Documentation built in 1.23 s
INFO     -  [12:00:00] Watching paths for changes
INFO     -  [12:00:00] Serving on http://127.0.0.1:8000/
```

Step 3: Access the address shown in the terminal in a browser to preview the documentation (if multi-language or version paths are configured, use the actual output).

> [!NOTE]NOTE
>
> * **`mkdocs serve`** listens on port **`8000`** by default. If that port is occupied, specify another address and port with **`-a`**, for example **`mkdocs serve -a 127.0.0.1:8080`**.
> * To detect link/anchor issues locally as early as possible, add **`--strict`**: **`mkdocs serve --strict`**. Read the Docs is currently configured with **`fail_on_warning: false`** (see **`.readthedocs.yaml`**), but you can still enable it locally to reduce silent errors.

## Static Build (Generating a Publishable Site)

To generate site artifacts that can be hosted on a static server (such as Nginx or object storage):

```shell
mkdocs build
```

The artifacts are output to **`site/`** in the repository root directory by default. Warnings can be treated as errors:

```shell
mkdocs build --strict
```

For the online documentation build process, see **`.readthedocs.yaml`** (which uses **`requirements/mkdocs.txt`** to install dependencies and reads the root **`mkdocs.yml`**).

## Common Issues

### Dependency Installation Failure

If dependency conflicts or installation failures occur during **`pip install`**, it is recommended to use a virtual environment for isolation:

```shell
python -m venv .venv_mkdocs
source .venv_mkdocs/bin/activate
pip install -r requirements/mkdocs.txt
```

### YAML Parsing Errors or `!!python/name:` Tag Exceptions

Extensions such as **`pymdownx.superfences`** and **`pymdownx.emoji`** in **`mkdocs.yml`** use the **`!!python/name:`** YAML tag, which is incompatible with PyYAML **`safe_load`**. The **`check-yaml`** hook in **`pre-commit`** has already applied an **`exclude`** to **`mkdocs.yml`** (see the repository's **`.pre-commit-config.yaml`**). If other local YAML validations report warnings, you can exclude **`mkdocs.yml`** in the same way.

### Navigation Does Not Update as Expected

The navigation of this repository is driven by **`docs/en/.nav.yaml`**. After adding a new page, add an entry in this file and verify the YAML indentation. After saving, restart **`mkdocs serve`** to refresh the sidebar.

### `extra.css` / `mathjax.js` Preview Returns 404

If requests to **`mkdocs/stylesheets/extra.css`** or **`mkdocs/javascripts/mathjax.js`** return **404**, verify that **`docs/en/mkdocs`** is a valid symbolic link pointing to **`docs/mkdocs`**, and that the paths in **`mkdocs.yml`** are correct relative to **`docs/en`**.

### CI Gate Reports "Local Path Inaccessible" for Internal Links

The CI gate typically resolves local links in Markdown using **`docs/en`** as the root. Avoid linking to **`*.md`** files outside **`docs/en`** (unless you convert them to internal paths or bring the content into **`docs/en`**). For descriptions of example directories in other repositories, place them under **`examples/`** and provide the in-repository path as text in the body, or use a browse link on **`repo_url`**.
