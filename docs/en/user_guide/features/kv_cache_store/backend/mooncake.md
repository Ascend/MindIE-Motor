# Mooncake Backend Feature

## Feature Introduction

The Mooncake backend implements cross-engine KV Cache sharing through a distributed shared memory pooling mechanism and is natively integrated by vLLM Ascend, so **no additional components need to be installed**. This feature allows Prefill engines to store KV Cache into a shared pool and Decode engines to read it from the pool, implementing KV cache reuse in PD disaggregation scenarios and reducing repeated computation.

### How It Works

The Mooncake backend uses a distributed shared memory pool architecture. It manages global pooling metadata through the `mooncake_master` process, and each engine node contributes pooled memory to or consumes pooled memory from the pool through the `mooncake_store_service` process. Its core workflow is as follows:

1. **Pooled memory registration**: Each node registers its own storage node information through mooncake_master, forming a globally visible distributed KV pool.

2. **KV written into the pool**: The Prefill engine writes the computed KV Cache into the shared pool in 128-token chunks through the AscendStoreConnector.

3. **KV read from the pool**: The Decode engine reads the required KV Cache blocks from the shared pool through the AscendStoreConnector.

4. **P2P direct transfer**: Supports direct transfer from Prefill to Decode through MooncakeConnectorV1 (without writing into the pool), reducing latency.

Mooncake pooling has two deployment modes (store_mode values), which differ in who contributes the pooled memory:

- **Embedded mode** (default; store_mode is empty or "embedded"): The engine process itself contributes `global_segment_size` of pooled memory. The configuration is the simplest and suitable for small-scale verification. **NOTE**: If the engine process crashes, the pooled memory it contributes becomes invalid.

- **Standalone mode** (store_mode="standalone"): Pooled memory is contributed by an independent mooncake_store_service process and is decoupled from the engine lifecycle, which is suitable for production deployment. The store process applies for large memory independently (it starts before the engines to avoid competing with engine weights/KV memory), and engine faults or rebuilds do not affect the existing data in the pool. Store process faults are restarted in place by the NodeManager (controlled by MOTOR_RESTART_LOCAL_SERVICE, enabled by default), and the process is re-registered with the master.

### Core Functions

- **Cross-engine KV sharing**: Prefill and Decode engines share KV Cache to avoid repeated computation.

- **P2P direct transfer**: Supports direct KV transfer from Prefill to Decode (MooncakeConnectorV1) without going through the storage pool, reducing transfer latency.

- **Automatic eviction**: Supports an automatic eviction mechanism based on the watermark (eviction_high_watermark_ratio / eviction_ratio), which automatically evicts old data when the pooled space usage reaches the threshold.

- **Multi-service sharing**: Supports cross-service sharing of the KV storage pool through the target_job_id configuration.

- **Multi-hardware adaptation**: Supports multiple hardware platforms such as Ascend 950PR products, Atlas 800I A3s, and Atlas 800I A2s.

| Hardware | Dependency | Description |
|------|------|------|
| Ascend 950PR products | <ul><li>HDK >= 25.6</li><li>mooncake >= v0.3.11</li><li>CANN >= 9.1.0</li></ul>  | UBOE or UB environment variables must be configured according to the actual communication protocol. |
| Atlas 800I A3 | <ul><li>HDK >= 26.0 or (HDK >= 25.5 and mooncake >= v0.3.11)</li><li>CANN >= 9.1.0</li><li>Lingqu computing network >= 1.5</li></ul> | Enabling the unified memory address direct transfer solution is recommended. |
| Atlas 800I A2 | <ul><li>HDK >= 25.5</li><li>CANN >= 9.1.0</li></ul> | No additional environment variables are required. The general mandatory items are sufficient. |

>[!NOTE]NOTE
>
>- All hardware requires the `HCCL_INTRA_ROCE_ENABLE=1` and `ASCEND_LOCAL_COMM_RES={"version":"1.3"}` environment variables. If they are missing, KV transfer fails or the `EI0014` error is reported.
>- `deploy.py` enforces validation of the `eviction_high_watermark_ratio` and `eviction_ratio` parameters for the Mooncake backend. If they are missing, an error is reported directly, so they must be configured explicitly.
>- In embedded mode, the pooled memory contributed by the engine process becomes invalid if the process crashes.
>- In standalone mode, the configuration file of the store process is automatically generated by the NodeManager and does not need to be configured manually.
>- Short requests (prompt < 128 tokens) are not written into the pool and generate no put traffic. This is the designed behavior of vLLM Ascend rather than a fault.

## Using the Feature

### Environment Preparation

**General environment variable configuration (required for all hardware):**

Configure the following environment variables in motor_engine_prefill_env and motor_engine_decode_env of env.json, and keep Prefill and Decode consistent.

```json
"motor_engine_prefill_env": {
  "HCCL_INTRA_ROCE_ENABLE": "1",
  "ASCEND_LOCAL_COMM_RES": "{\"version\":\"1.3\"}"
}
```

**Table 2** Environment variable description

| Environment Variable | Description |
|------|------|
| HCCL_INTRA_ROCE_ENABLE=1 | **Mandatory**.<ul><li>The underlying HIXL direct transfer uses the RoCE protocol, which must be explicitly enabled to establish a connection. If it is not configured, KV transfer fails.</li><li>This variable must be configured in motor_engine_prefill_env / motor_engine_decode_env and delivered to the engine Pods with the deployment. Exporting it only in the shell of the deployment node does not take effect.</li></ul> |
| ASCEND_LOCAL_COMM_RES={"version":"1.3"} | **Mandatory**.<ul><li>Makes ascend_transport generate local communication resources in v1.3 format and use client-server one-sided communication, with `device_port` carried in the ranktable. It must be configured on all hardware.</li><li>In standalone mode, if it is missing, the store process and the engine worker share the same NPU, duplicate device_ip occurs in the merged ranktable, and `EI0014: IP is used repeatedly` is reported, which makes block pooling fail for the worker on the same card as the store (for example, TP rank 0).</li></ul> |

**Table 3** Hardware-specific environment variable configuration

| Hardware | Environment Variable | Description |
|-------|-------|------|
| Ascend 950PR products | <ul><li>When the UBOE protocol is used: ASCEND_GLOBAL_RESOURCE_CONFIG={"comm_resource_config.protocol_desc":["uboe:device"]}</li><li>When the UB protocol is used: ASCEND_LOCAL_COMM_RES={"version":"1.3"}</li></ul> | Choose either UBOE or UB, and configure it according to the communication protocol actually used. |

If SSD offload is enabled, the related memory size must be aligned to 1 GB. | Atlas 800I A3 | ASCEND_BUFFER_POOL=4:8 | Used when the software versions in the dependency column of [Table 1](#table001) are not met.<br>Configures the number and size of buffers on the NPU device used for aggregation and KV transfer (for example, `4:8` indicates four 8 MB buffers). |
| Atlas 800I A2 | — | No additional environment variables are required. The general mandatory items are sufficient. |

### Usage Scenarios

**Scenario 1: Embedded mode (small-scale verification)**

- Applicable scenario: development and test environments, small-scale verification, and rapid prototyping.

- Characteristics: The simplest configuration. The engine process itself contributes pooled memory, and no additional store process needs to be deployed.

- Limitation: The pooled memory becomes invalid if the engine process crashes, so this mode is not suitable for production environments.

**Scenario 2: Standalone mode (production deployment)**

- Applicable scenario: production environments, PD disaggregation deployment, and high availability requirements.

- Characteristics: Pooled memory is contributed by an independent `mooncake_store_service` process and is decoupled from the engine lifecycle. Engine faults or rebuilds do not affect the existing data in the pool.

- Benefits: The store process applies for large memory independently, avoiding competition with engine weights/KV memory. Store process faults can be automatically recovered by the NodeManager.

### Usage Example

#### Scenario 1: Embedded Mode Configuration

1. Configure the Mooncake backend field kv_cache_store_config in the user_config.json configuration file. The example is as follows.

    ```json
    "kv_cache_store_config": {
      "enable": true,
      "backend": "mooncake",
      "global_segment_size": "2GB",
      "eviction_high_watermark_ratio": 0.9,
      "eviction_ratio": 0.1
    }
    ```

    **Table 4** Parameter description

    | Field | Default Value | Mandatory | Description |
    |------|--------|------|------|
    | enable | false | Yes | Master switch for pooling. It must be set to: true. |
    | backend | memcache | Yes | It must be set to: "mooncake". |
    | global_segment_size | None | Yes | Size of the pooled memory contributed by the engine process, for example: "2GB". |
    | eviction_high_watermark_ratio | None | Yes | Eviction watermark threshold. The recommended value is: 0.9; `deploy.py` enforces validation and reports an error if it is missing. |
    | eviction_ratio | None | Yes | Single eviction ratio. The recommended value is: 0.1; `deploy.py` enforces validation and reports an error if it is missing. |

    >[!NOTE]NOTE
    >The optional parameter `target_job_id` can be configured to reuse the kv_store of another inference service (the value is the `job_id` of the target service). For details, see [Sharing kv_store Across Multiple Services](../README.md#table_Connector).

2. Configure the general environment variables in `env.json` by referring to the [Environment Preparation](#environment-preparation) section, and ensure that the Prefill and Decode configurations are consistent.

3. Start the service by using the deployment script.

    ```bash
    cd examples/deployer
    python deploy.py --config_dir <configuration directory>
    ```

    >[!NOTE]NOTE
    >`<configuration directory>` is the directory containing the `user_config.json` and `env.json` that have been configured for Mooncake as described above. Replace it with the actual path.

    After deployment, a sign that the `mooncake master` connection is successful should appear in the log, which indicates that kv_cache_store initialization is complete.

    | Field | Default Value | Mandatory | Description |

    | kv_role | — | Yes | <ul><li>Prefill: set to "kv_producer"</li><li>Decode: set to "kv_consumer"</li></ul> |
    | engine_id | — | Yes | Pooling domain identifier. It must be configured and kept consistent between P and D. |
    | kv_port | — | Recommended | It is recommended to specify it explicitly (for example, `"30001"`) to avoid port conflicts among multiple services. |
    | connectors[].MooncakeConnectorV1 | — | Yes | P2P direct transfer (KV is transferred directly from prefill to decode without being written into the pool). The `prefill`/`decode` topology must be consistent with the deployment. |
    | connectors[].AscendStoreConnector | — | Yes | Pool storage (prefill writes into the pool / decode reads from the pool). `backend` must be set to `"mooncake"`. |

3. Configure the general environment variables in `env.json` by referring to the [Environment Preparation](#environment-preparation) section, and ensure that the Prefill and Decode configurations are consistent.

4. Start the service by using the deployment script.

    ```bash
    cd examples/deployer
    python deploy.py --config_dir <configuration directory>
    ```

    >[!NOTE]NOTE
    >`<configuration directory>` is the directory containing the `user_config.json` and `env.json` that have been configured for Mooncake as described above. Replace it with the actual path.

    The NodeManager automatically starts the mooncake_store_service process and automatically generates the store configuration file.
    After deployment is complete:

    - A sign of a successful mooncake master connection should appear in the log.
    - The store process configuration file is automatically generated in the same directory as the engine configuration (mooncake_store_config.json).
    - Both the Prefill and Decode engines are successfully registered with mooncake_master.

    >[!NOTE]NOTE
    >
    >- The configuration file of the store process is automatically generated by the NodeManager in the same directory as the engine configuration (mooncake_store_config.json). local_hostname uses the POD_IP, and the master address uses the KVS_MASTER_SERVICE.
    >- The communication environment of the store process is also automatically configured by the NodeManager without manual intervention: the store exclusively uses HIXL comm_resource_config.listen_port=26666 (written into the device_port of the ranktable to distinguish it from the engine worker on the same card and avoid HCCL EI0014), and the HCCL socket port range is offset from that of the engine (Atlas 800I A2: HCCL_NPU_SOCKET_PORT_RANGE=16700-16800; Ascend 950PR products: host socket range +2000), avoiding conflicts with the engine's 16666/RA socket (EI0020).

#### Scenario 3: Additional Configuration for Ascend 950PR products

When the Mooncake backend is used on Ascend 950PR products, ensure that the Pod can access the host-side UB-related NICs (ipourma*). Choose either of the following methods.

**Method 1: Using the Host Network**

1. Configure the host network for Prefill / Decode.
   In the default CRD deployment (`deploy_mode` is `infer_service_set`), edit examples/deployer/yaml_template/infer_service_template.yaml, and add the following fields under spec.template.spec in both the `- name: prefill` and `- name: decode` definitions in roles (both must be configured):

   ```yaml
   - name: prefill   # Modify the decode role in the same way
     # ...
     spec:
       template:
         spec:
           hostNetwork: true
           dnsPolicy: ClusterFirstWithHostNet
           schedulerName: volcano
           # ... Keep the remaining original fields unchanged
   ```

   >[!NOTE]NOTE
   >If motor_deploy_config.deploy_mode in user_config.json is multi_deployment, modify examples/deployer/yaml_template/engine_template.yaml: add the same fields as above (hostNetwork: true, dnsPolicy: ClusterFirstWithHostNet) under spec.template.spec of the engine Pod.

2. Add the Ascend 950PR products engine environment variables.
   Edit set_a5_engine_env in examples/deployer/startup/common.sh (invoked by roles/engine.sh in the Ascend 950PR products scenario), and complete the implementation as follows:

   ```bash
   set_a5_engine_env() {
       local if_name ip
       if_name=$(awk '$2 == "00000000" {print $1; exit}' /proc/net/route)
       ip="${HOST_IP:-$POD_IP}"

       if [ -z "$if_name" ]; then
           # Skip auto-detection only; never unset — the user may have exported these explicitly.
           echo "Warning: failed to detect default route interface from /proc/net/route, skip GLOO/TP/HCCL socket ifname env" >&2
       else
           export GLOO_SOCKET_IFNAME="$if_name"
           export TP_SOCKET_IFNAME="$if_name"
           export HCCL_SOCKET_IFNAME="$if_name"
       fi

       if [ -z "$ip" ]; then
           # Skip auto-detection only; never unset — the user may have exported it explicitly.
           echo "Warning: HOST_IP and POD_IP are both empty, skip HCCL_IF_IP env" >&2
       else
           export HCCL_IF_IP="$ip"
       fi

       export PATH="$PATH:/usr/local/go/bin"
       export LD_LIBRARY_PATH="/usr/local/lib:/lib64:${LD_LIBRARY_PATH:-}"
       export ASCEND_LOCAL_COMM_RES_PATH="${ASCEND_LOCAL_COMM_RES_PATH:-/etc/hixlep}"
   }
   ```

   >[!NOTE]NOTE
   >The script above selects the first NIC of the default route from /proc/net/route as the `GLOO`/`TP`/`HCCL` communication NIC. Ensure that this NIC is the primary NIC of the server.

3. Redeploy the service.

    ```bash
    cd examples/deployer
    python deploy.py --config_dir <configuration directory>
    ```

    >[!NOTE]NOTE
    >`<configuration directory>` is the directory containing the `user_config.json` and `env.json` that have been configured for Mooncake as described above. Replace it with the actual path.

**Method 2: Mounting the Host ipourma NICs into the Pod**

The following mount operations must be performed separately on **each server where inference instances are deployed**.

**Mounting into the Pod:**

1. Back up IPv6.

   ```bash
   BACKUP=/tmp/ipourma_backup_latest.txt
   : > "$BACKUP"
   for i in $(seq 0 9); do
     echo "===== ipourma$i =====" | tee -a "$BACKUP"
     ip -6 addr show dev ipourma$i 2>/dev/null | tee -a "$BACKUP"
   done
   ```

2. Locate the business container and query its PID.

   Run `docker ps` on the local machine, and distinguish the pause sandbox from the inference business container by container name. Under Docker, K8s container names are roughly as follows:

   ```text
   k8s_<container name>_<Pod name>_<namespace>_<PodUID>_<retry count>
   ```

   | Fragment | Description | Example |
   |------|------|------|
   | k8s_POD_... | pause sandbox, not required | k8s_POD_vllm-0-decode-0-0_mindie-motor_... |
   | k8s_vllm_... | business container (the container name in the image is usually: vllm) |k8s_vllm_vllm-0-decode-0-0_mindie-motor_... |

   >[!NOTE]NOTE
   >`k8s_vllm_...` is the business container. Subsequent operations, including PID retrieval and NIC mounting, are all performed on this container.
   >
   >```bash
   ># Replace <Pod name keyword> with the actual value, for example, vllm-0-decode-0-0; exclude the k8s_POD_ sandbox
   >CNAME=$(docker ps --format '{{.Names}}' | grep '<Pod name keyword>' | grep -v 'k8s_POD_' | head -1)
   >PID=$(docker inspect -f '{{.State.Pid}}' "$CNAME")
   >echo "CNAME=$CNAME PID=$PID"
   >```

3. Expose the network namespace.

   Replace `<custom name>` with a memorable name (such as `decode` or `prefill`):

   ```bash
   NS_NAME=<custom name>
   mkdir -p /var/run/netns
   ln -sf /proc/$PID/ns/net /var/run/netns/$NS_NAME
   ip netns list
   ```

4. Move the NICs into the Pod.

   ```bash
   for i in $(seq 0 9); do
     ip link show dev ipourma$i >/dev/null 2>&1 && ip link set ipourma$i netns "$NS_NAME"
   done
   ```

5. Enable IPv6 in the Pod netns, bring up the NICs, and restore the addresses.

   ```bash
   ip netns exec "$NS_NAME" sysctl -w net.ipv6.conf.all.disable_ipv6=0
   ip netns exec "$NS_NAME" sysctl -w net.ipv6.conf.default.disable_ipv6=0

   cur_dev=""
   while IFS= read -r line; do
     if [[ "$line" =~ ^=====[[:space:]]+(ipourma[0-9]+) ]]; then
       cur_dev="${BASH_REMATCH[1]}"
       ip netns exec "$NS_NAME" sysctl -w net.ipv6.conf.${cur_dev}.disable_ipv6=0 || true
       ip netns exec "$NS_NAME" ip link set "$cur_dev" up || true
     elif [[ "$line" =~ inet6[[:space:]]+([^/]+)/([0-9]+) ]]; then
       addr="${BASH_REMATCH[1]}"; pref="${BASH_REMATCH[2]}"
       [ -n "$cur_dev" ] && [ "$addr" != "::1" ] && \
         ip netns exec "$NS_NAME" ip -6 addr add "$addr/$pref" dev "$cur_dev" 2>/dev/null || true
     fi
   done < "$BACKUP"
   ```

6. Verify with the following commands.

   ```bash
   ip netns exec "$NS_NAME" ip -br link | grep ipourma
   nsenter -t "$PID" -n python3 -c "import socket; print(socket.if_nametoindex('ipourma0'))"
   ```

   After the mount succeeds, NICs such as `ipourma0` to `ipourma9` should be visible in the container (the specific names and addresses depend on the actual environment).

**Moving back to the host (rollback):**

Execute this before deleting or recreating the Pod. `<name used at that time>` must be consistent with the NS_NAME used when mounting:

```bash
NS_NAME=<name used at that time>
BACKUP=/tmp/ipourma_backup_latest.txt

# 1. Move from the Pod netns back to the host
for i in $(seq 0 9); do
  ip netns exec "$NS_NAME" ip link show dev ipourma$i >/dev/null 2>&1 && \
    ip netns exec "$NS_NAME" ip link set ipourma$i netns 1
done

# 2. Restore IPv6 on the host
sysctl -w net.ipv6.conf.all.disable_ipv6=0
sysctl -w net.ipv6.conf.default.disable_ipv6=0

cur_dev=""
while IFS= read -r line; do
  if [[ "$line" =~ ^=====[[:space:]]+(ipourma[0-9]+) ]]; then
    cur_dev="${BASH_REMATCH[1]}"
    sysctl -w net.ipv6.conf.${cur_dev}.disable_ipv6=0 || true
    ip link set "$cur_dev" up || true
  elif [[ "$line" =~ inet6[[:space:]]+([^/]+)/([0-9]+) ]]; then
    addr="${BASH_REMATCH[1]}"; pref="${BASH_REMATCH[2]}"
    [ -n "$cur_dev" ] && [ "$addr" != "::1" ] && \
      ip -6 addr add "$addr/$pref" dev "$cur_dev" 2>/dev/null || true
  fi
done < "$BACKUP"

# 3. Delete the soft link
rm -f /var/run/netns/"$NS_NAME"

# 4. Confirm
ip -br link | grep ipourma
```

>[!NOTE]NOTE
>
>- An ipourma interface can belong to only one network namespace at a time. Multiple engine Pods on the same node must not contend for the same set of interfaces.
>- If the Pod is deleted without rollback, the NICs may be lost and can be recovered only by reloading the driver or restarting the node.
>- If "IPv6 is disabled on this device" is reported, run `sysctl -w net.ipv6.conf.<NIC>.disable_ipv6=0` on the interface first.

### Verification

**Prerequisites for verification:** Use a long prompt (>= 128 tokens; 500+ tokens recommended) to initiate requests. Short requests (prompt < 128 tokens) are not written into the pool and generate no put traffic. This is normal behavior, not a fault.

**Verification steps:**

1. Use curl or a similar tool to query metrics from the `mooncake_master` service:

   ```bash
   curl http://<master-ip>:<master-port>/metrics | grep -E "PutStart|Keys"
   ```

2. Check the `mooncake_master` logs to confirm that there are records of KV blocks being written into the pool.

3. Observe the Decode engine logs to confirm that there are records of KV blocks being read from the pool.

**Expected output:**

- The `PutStart` count should be greater than 0, indicating that blocks are successfully written into the pool.
- The `Keys` list should contain the key identifiers of the corresponding blocks.
- If `MooncakeConnectorV1` P2P direct transfer is used, direct transfer records from Prefill to Decode can be observed.

## Tuning Suggestions

| Parameter | Scenario | Recommended Configuration | Description |
|------|------|----------|------|
| global_segment_size | General | 1.5 to 2 times the estimated KV Cache size of the model | Adjust it based on the model size and concurrency. A value that is too small causes frequent eviction, while a value that is too large wastes NPU memory. |
| eviction_high_watermark_ratio | General | 0.9 | In high-concurrency scenarios, it can be moderately reduced to reduce eviction jitter. |
| eviction_ratio | General | 0.1 | In high-concurrency scenarios, it can be moderately reduced to reduce eviction jitter. |
| default_kv_lease_ttl | High-latency scenarios | Greater than the transfer timeout (ASCEND_CONNECT_TIMEOUT / ASCEND_TRANSFER_TIMEOUT) | Controls the lease validity period of KV objects to prevent the lease from expiring before the transfer is complete. |

**Parameter interaction description:**

- `global_segment_size` and `eviction_high_watermark_ratio` jointly determine the actual memory threshold that triggers eviction: `actual trigger threshold = global_segment_size × eviction_high_watermark_ratio`.
- In high-concurrency scenarios, it is recommended to reduce both `eviction_high_watermark_ratio` and `eviction_ratio` to reduce the superimposed impact of eviction operations on service jitter.
- `default_kv_lease_ttl` must be set together with the transfer timeout to ensure that the lease lifetime is greater than the slowest transfer completion time, preventing the KV from being reclaimed during transfer.

## FAQs

### EI0014: IP is used repeatedly Is Reported After Deployment

**Symptom**

When the service is deployed in standalone mode, the engine Pod reports the EI0014: IP is used repeatedly error during startup.

**Cause Analysis**

In standalone mode, the store process and the engine worker share the same NPU, and a duplicate `device_ip` occurs when the ranktables are merged. This is because `ASCEND_LOCAL_COMM_RES={"version":"1.3"}` is not configured, so ascend_transport does not generate local communication resources in v1.3 format.

**Solution**

1. Confirm that the following is configured in `motor_engine_prefill_env` and `motor_engine_decode_env` of `env.json`:

   ```json
   "ASCEND_LOCAL_COMM_RES": "{\"version\":\"1.3\"}"
   ```

2. Redeploy the service.

### KV Transfer Fails and Engines Cannot Establish a Connection

**Symptom**

KV transfer cannot be completed between the Prefill and Decode engines, and there are no transfer records in the logs.

**Cause Analysis**

`HCCL_INTRA_ROCE_ENABLE=1` is not configured, so the RoCE protocol is not enabled for the underlying HIXL direct transfer, and connection establishment fails.

**Solution**

1. Confirm that the following is configured in `motor_engine_prefill_env` and `motor_engine_decode_env` of `env.json`:

   ```json
   "HCCL_INTRA_ROCE_ENABLE": "1"
   ```

2. Confirm that this variable is configured in `env.json` and delivered to the engine Pods with the deployment, rather than being exported only in the shell of the deployment node.

3. Redeploy the service.

### eviction_high_watermark_ratio or eviction_ratio Missing During Deployment

**Symptom**

When deploy.py is used to deploy the Mooncake backend, an error is reported indicating that `eviction_high_watermark_ratio` or `eviction_ratio` is missing.

**Cause Analysis**

deploy.py enforces validation of these two parameters for the Mooncake backend, and they must be configured explicitly. They cannot be omitted even if default values exist.

**Solution**

1. Configure them explicitly in `kv_cache_store_config`:

   ```json
   "eviction_high_watermark_ratio": 0.9,
   "eviction_ratio": 0.1
   ```

2. The recommended values are 0.9 and 0.1 respectively, and they can be adjusted based on the actual scenario.

3. Run the deployment again.

### No Pooling Behavior Observed When Verifying with Short Requests

**Symptom**

When a short prompt (< 128 tokens) is used to verify the pooling function, the `PutStart` and `Keys` metrics are not observed on the mooncake_master side.

**Cause Analysis**

`AscendStoreConnector` determines whether to write into the pool (`can_save`) at a chunk granularity of 128 tokens, and a put is actually triggered only when the number of tokens reaches a complete chunk. Short requests (prompt < 128 tokens) are not written into the pool and generate no put traffic. This is the designed behavior of vLLM Ascend rather than a fault.

**Solution**

1. Use a long prompt (>= 128 tokens; 500+ tokens recommended) to initiate a request.

2. Confirm that the block is actually written into the pool by observing metrics such as `PutStart`/`Keys` on the master side:

   ```bash
   curl http://<master-ip>:<master-port>/metrics | grep -E "PutStart|Keys"
   ```
