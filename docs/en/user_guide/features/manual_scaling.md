# Manual Scaling

## Feature Introduction

The manual scaling feature adjusts the number of engine instances on a cluster that has been fully deployed by modifying the instance numbers in `user_config.json` and running `--update_instance_num`, thereby implementing scale-out (adding instances) or scale-in (removing instances).

### Constraints and Limitations

| Constraint Dimension | Requirement |
|----------|------|
| Hardware | <ul><li>Atlas 800I A2</li><li>Atlas 800I A3</li></ul>Manual scaling has no additional hardware restrictions and uses the same server model as the deployed service. |
| Deployment scenario | PD disaggregation (modifying `p_instances_num` and `d_instances_num`) and PD aggregation (modifying `hybrid_instances_num`) are supported. |
| Engine | vLLM and SGLang are supported. Scaling does not switch the engine, and the `engine_type` must be consistent with that of the deployed service. |
| Software dependency | The kubectl permission of the K8s cluster administrator is required, and the ConfigMap `motor-config` generated by a full deployment must exist in the cluster. |
| Other limitations | <ul><li>During scaling, only the `motor_deploy_config.p_instances_num`, `motor_deploy_config.d_instances_num`, and `motor_deploy_config.hybrid_instances_num` fields are allowed to be modified;</li><li>The number of instances must be greater than 0 and not exceed 16; otherwise, an error occurs during deployment or scaling;</li><li>Scaling affects only engine instances; the controller and coordinator are not updated in the scaling process;</li><li>To modify non-instance-number configurations such as images and mount paths, redeploy the service;</li><li>Scaling in deletes instances starting from the highest index and synchronously deletes the corresponding engine YAML files under `output/deployment/`;</li><li>The baseline of the deployed configuration is the user_config in the ConfigMap (motor-config) within the cluster;</li><li>The Prefix Cache feature is enabled by default. This feature reuses the computed KV Cache. Newly scaled-out instances have no KV Cache, so their inference performance may degrade slightly and recover after a period of time.</li></ul> |

## Feature Usage

### Environment Preparation

- Environment deployment has been completed by referring to [PD Aggregation Service Deployment](../deployment/k8s/pd_aggregation_deployment.md), [PD Disaggregation Service Deployment](../deployment/k8s/pd_disaggregation_deployment.md), or [SGLang PD Disaggregation Service Deployment](../deployment/k8s/pd_disaggregation_sglang.md).
- At least one full deployment has been completed successfully (a ConfigMap `motor-config` exists in the cluster, containing the currently deployed user_config as the baseline).
- You have the kubectl permission of the K8s cluster administrator.

### Application Scenarios

**Scenario 1: PD disaggregation**

Applicable to the scenario where Prefill and Decode are deployed separately. The numbers of P and D instances are adjusted by modifying `p_instances_num` and `d_instances_num`, respectively.

**Scenario 2: PD aggregation**

Applicable to the scenario where Prefill and Decode are deployed in a combined manner. The number of union instances is adjusted by modifying `hybrid_instances_num`.

### Usage Examples

#### Scenario 1: PD Disaggregation

1. For the first deployment, run the following commands in the `examples/deployer` directory to perform a full deployment. `{namespace}` must be the same as `job_id` in `user_config.json`.

   ```bash
   kubectl create namespace {namespace}
   cd examples/deployer
   # Method 1: Specify the configuration directory (recommended)
   python3 deploy.py --config_dir ../../model_configs/vllm --nostep

   # Method 2: Specify configuration files individually
   python3 deploy.py --user_config_path ../../model_configs/vllm/user_config.json --env_config_path ../../model_configs/vllm/env.json --nostep
   ```

   Parameter description:
   - `--config_dir`: specifies the configuration directory path.
   - `--user_config_path`: specifies the user_config.json path separately.
   - `--env_config_path`: specifies the env.json path separately.

   After the execution is complete:
   - The ConfigMap `motor-config` is created or updated in the cluster (its content comes from the current `user_config.json` input), serving as the baseline for subsequent scaling and refresh operations.
   - When the deployment is successful, `all deploy end.` and `Deploy complete.` appear in the logs.

2. Modify the instance numbers in `user_config.json` as required. The parameters to be modified are `p_instances_num` and `d_instances_num`. For more parameter descriptions, see [Full Parameter Reference of the user_config.json Configuration File](../configuration/config_reference.md#motor_deploy_config).

   **Table 1** Parameter description of PD disaggregation instance numbers

   | Configuration Item | Type | Value Range | Mandatory | Default Value | Description |
   |--------|------|----------|------|--------|------|
   | motor_deploy_config.p_instances_num | int | [1, 16] | Yes | 1 | Number of Prefill instances. |
   | motor_deploy_config.d_instances_num | int | [1, 16] | Yes | 1 | Number of Decode instances. |

   Configuration example (scaling out P instances from 1 to 2 while D instances remain 1):

   ```json
   {
     "motor_deploy_config": {
       "p_instances_num": 2,
       "d_instances_num": 1
     }
   }
   ```

3. Run the scaling command in the `examples/deployer` directory.

   ```bash
   python3 deploy.py --config_dir ../../model_configs/vllm --update_instance_num --nostep
   ```

   > [!NOTE]NOTE
   > If the deployment was performed by specifying configuration files individually, you must also specify `--user_config_path` and `--env_config_path` during scaling.

   Parameter description:
   - `--update_instance_num`: specifies the scaling mode. The baseline comes from the cluster ConfigMap (motor-config); compared with the current input, only instance number changes are allowed.
   - `--config_dir`: specifies the configuration directory path.
   - `--user_config_path`: specifies the user_config.json path separately.
   - `--env_config_path`: specifies the env.json path separately.

   When scaling is successful, `instance num update end.` appears in the logs.

   > [!NOTE]NOTE
   >- The baseline comes from the cluster ConfigMap (motor-config). Compared with the current input, only instance number changes are allowed.
   >- Scale-out: run kubectl apply only for the newly added instance indexes. Running instances are not re-pulled.
   >- Scale-in: delete instances in sequence starting from the highest index, and synchronously delete the corresponding engine YAML files under `output/deployment/`.
   >- After scaling succeeds, the ConfigMap is updated to the current input `user_config.json`.

### Verification

The following uses PD disaggregation as an example, in which `p_instances_num` is scaled out from 1 to 2 and then scaled in back to 1. In the commands, `{namespace}` must be replaced with the actual namespace and must be the same as `job_id`.

1. Check whether the scaling command is successful.

   When it is successful, the following appears in the deploy logs:

   ```text
   instance num update end.
   ```

2. Check whether the instance numbers in the ConfigMap have been updated.

   ```bash
   kubectl get configmap motor-config -n {namespace} -o jsonpath='{.data.user_config\.json}' | python3 -c "import sys,json; d=json.load(sys.stdin); c=d['motor_deploy_config']; print('p_instances_num=', c.get('p_instances_num'), 'd_instances_num=', c.get('d_instances_num'))"
   ```

   After scaling out to 2 P instances, the command output is as follows:

   ```text
   p_instances_num= 2 d_instances_num= 1
   ```

   After scaling in back to 1 P instance, the command output is as follows:

   ```text
   p_instances_num= 1 d_instances_num= 1
   ```

3. Check the engine instance status.

   ```bash
   kubectl get pod -n {namespace}
   ```

   After scale-out, the newly added engine instances with higher indexes are in the Running state. The command output is as follows:

   ```text
   NAME                         READY   STATUS    RESTARTS   AGE
   vllm-0-controller-0-xxx      1/1     Running   0          1m
   vllm-0-coordinator-0-xxx     1/1     Running   0          1m
   vllm-0-decode-0-0            1/1     Running   0          1m
   vllm-0-prefill-0-0           1/1     Running   0          1m
   vllm-0-prefill-1-0           1/1     Running   0          20s
   ```

   After scale-in, the instances with higher indexes enter the Terminating state and are deleted. The command output is as follows:

   ```text
   NAME                         READY   STATUS        RESTARTS   AGE
   vllm-0-controller-0-xxx      1/1     Running       0          2m
   vllm-0-coordinator-0-xxx     1/1     Running       0          2m
   vllm-0-decode-0-0            1/1     Running       0          2m
   vllm-0-prefill-0-0           1/1     Running       0          2m
   vllm-0-prefill-1-0           1/1     Terminating   0          1m
   ```

4. Check whether the number of InferServiceSet role replicas is consistent with the configuration.

   ```bash
   kubectl get inferserviceset vllm -n {namespace} -o jsonpath='{range .spec.template.roles[*]}{.name} replicas={.replicas}{"\n"}{end}'
   ```

   After scale-out, the command output is as follows:

   ```text
   prefill replicas=2
   decode replicas=1
   ```

   After scale-in, the command output is as follows:

   ```text
   prefill replicas=1
   decode replicas=1
   ```

   In the PD aggregation scenario, replace `p_instances_num`/`prefill` in the preceding checks with `hybrid_instances_num`/`union`.

## FAQs

### ConfigMap motor-config not found or has no user_config in cluster

**Symptom**

When scaling is performed, the error `ConfigMap motor-config not found` or `has no user_config in cluster` is reported.

**Cause Analysis**

A full deployment has not been performed yet, or there is no motor-config in the corresponding namespace.

**Solution**

1. Confirm that the namespace has been created and is the same as `job_id`.
2. Perform a full deployment in the `examples/deployer` directory.

   ```bash
   cd examples/deployer
   python3 deploy.py --config_dir ../../model_configs/vllm --nostep
   ```

### user_config changes detected beyond instance numbers

**Symptom**

When scaling is performed, `user_config changes detected beyond instance numbers` is reported.

**Cause Analysis**

Configurations other than the instance numbers have been modified. The scaling process only allows `p_instances_num`, `d_instances_num`, or `hybrid_instances_num` to be changed.

**Solution**

1. Check `user_config.json` to ensure that only `p_instances_num`, `d_instances_num`, or `hybrid_instances_num` has been modified, and that other configuration items such as images, mount paths, and parallelism are not modified.
2. To compare with the baseline configuration, view the user_config in the cluster ConfigMap (motor-config).

   ```bash
   kubectl get configmap motor-config -n {namespace} -o jsonpath='{.data.user_config\.json}' | python3 -m json.tool
   ```

3. If non-instance-number configurations need to be modified, perform a full redeployment instead of using `--update_instance_num`.
